# Bash Code Stack

## Doc consultation: shell introspection builtins and the ShellCheck wiki

Bash's authority is the running shell, not a document: a name can be shadowed by a function or an alias, an option can have been flipped by a sourced file, and a construct can be missing from the interpreter that will actually execute the script. Query the shell, and pick the narrowest query:

| Need | Command | Typical size |
|---|---|---|
| Does this command exist — as a gate driving a branch or exit code | `command -v <name> >/dev/null 2>&1` | no stdout; exit status only |
| What class of thing is this name (alias, keyword, function, builtin, file) | `type -t <name>` | 1 word |
| What a bare word actually runs, and whether a builtin is shadowed | `type -a <name>` | 1–N lines, precedence order |
| Is this variable really a scalar, or an array / integer / exported | `declare -p <name>` | 1 line; exit 1 if unset |
| Is `errexit` / `pipefail` / `nullglob` / `globstar` in effect right now | `if shopt -q nullglob; then`, `if shopt -qo pipefail; then`, `[[ $- == *e* ]]` | exit status only |
| Which options does *this* bash even have | `shopt -p`, `set -o` | ~40 lines each |
| Which bash is this, for a version gate | `if (( BASH_VERSINFO[0] >= 4 )); then …`; `declare -p BASH_VERSINFO` for the dump | status only; 6 indices |
| What a builtin or reserved word does | `help <name>`, `help -s <name>` for the synopsis alone | 1 line to ~60 lines; `-s` prints one line per name the prefix matches |
| What a ShellCheck code means, with a bad/good pair | fetch `https://www.shellcheck.net/wiki/SC<code>` | one self-contained page |

`shopt` and `set -o` name two disjoint option sets: `shopt errexit` is an error, because errexit and pipefail are `set -o` options and reach `shopt` only through `-o`. Put every query inside a conditional, because every form returns 1 when the option is off, so under `set -e` a query written as a bare statement aborts the script; `-q`/`-qo` suppress the printed line and not that exit status, and `set +o <name>` is a mutation, not a query. `type`'s human-readable prose is not a parseable contract (POSIX fixes its exit status, not its wording), so branch on `command -v` and read `type -a` with your eyes. `help` covers builtins and reserved words only and hard-fails on anything else; `-s` works on bash 3.2, while `-d` and `-m` are 4.x additions. `BASH_VERSINFO` is present on bash 2.x+, so a version gate runs even on the shell it gates out — `bash --version`'s string is for humans, do not parse it.

Escalate past the builtins when: `type -a` shows the first hit is a file → `man <cmd> | col -b | grep -n 'PATTERN'`, because BSD/macOS `man` renders bold as doubled overstrike characters and a plain `grep 'BUILTIN COMMANDS'` returns zero hits on text that is plainly there; `type -a` says the first hit is a builtin → `man <name>` documents the unrelated external file, not the code that will run; a version boundary is load-bearing → the maintainer's NEWS file at `https://tiswww.case.edu/php/chet/bash/NEWS` or the bug-bash archive, never a blog post, since secondary sources disagree on real boundaries; behavior on the older interpreter is in question → no document settles it, run it under both and diff (`/bin/bash -c '…'` is 3.2.57 on macOS, PATH `bash -c '…'` is whatever was installed); a documented portability claim conflicts with the host → run the literal binary by absolute path, since an alias can answer for a bare name. When linting an entry script that sources modules, `shellcheck -x` alone is a false negative — `-x` follows the sourced file and clears the SC1091 notice, but findings originating inside that file stay suppressed until `-a`/`--check-sourced` is also passed; a module file with no shebang is still analyzed, but under a fallback dialect, so add `--shell=bash` or a `# shellcheck shell=bash` directive for dialect-correct results and to clear SC2148. The errexit checks are opt-in, not default: SC2310 (errexit suppressed in a conditional) needs `-o check-set-e-suppressed` and SC2312 (masked command-substitution status) needs `-o check-extra-masked-returns`; `shellcheck --list-optional` prints the full set.

Consultation is not required for: ordinary uses of well-established builtins and reserved words (`cd`, `if`/`then`/`fi`, `[[ ]]`, `(( ))`, plain `local`/`readonly`); a construct whose ShellCheck code and wiki page you already have; a version boundary already quoted from NEWS; a flag already confirmed portable. SC2002 (useless `cat`) is an optional check on current ShellCheck and stays advisory. SC2005 (`echo "$(cmd)"`) is not style-only, so do not apply it mechanically: `$( )` strips every trailing newline and reports only the substitution's status, so dropping it changes what the caller receives and when — take the fix where the value is a single line, and leave `echo "$(cmd)"` alone where the stripping or the buffering is what the code relies on.

## Footgun catalog

Scan every written line against these; apply them even when nearby code does not.

- **Unquoted expansion splits, then globs.** An unquoted `$var` or `$(cmd)` is first word-split on `$IFS` and then pathname-expanded against the real filesystem, so `pattern='*.txt'; printf '%s\n' $pattern` prints matching filenames rather than the literal string (SC2086, SC2046). Quote every expansion — `printf '%s\n' "$1"`, `for f in "$@"` — leaving it bare only inside `[[ … ]]`, a scalar assignment, or the subject word of a `case` — an unquoted expansion in a `case` *pattern* is glob-interpreted, which is sometimes wanted and never safe by default.
- **`"${arr[*]}"` where `"${arr[@]}"` was meant.** `"${arr[@]}"` produces one word per element, while `"${arr[*]}"` joins the whole array into a single word on the first character of `$IFS`, and unquoted `${arr[@]}` re-splits and re-globs every element — exactly what the array existed to prevent (SC2068). Write `"${arr[@]}"`, always quoted, and when a joined string is genuinely wanted scope the separator with `local IFS=,` inside a function rather than saving and restoring, since restoring an `IFS` that started *unset* leaves it set-but-empty and disables word splitting for everything after.
- **An unmatched glob expands to its own literal text.** `for f in ./*.log` with no matches iterates once with `f='./*.log'`, and the next command operates on a path that does not exist, surfacing later as an unrelated "no such file". Guard per iteration with `[[ -e $f || -L $f ]] || continue` — `-e` alone also drops a dangling symlink the glob legitimately matched — or set `shopt -s nullglob` and restore it after — shopt state is process-global and `source` runs in the same process, so any module sourced afterwards inherits a setting it never asked for.
- **The two test forms fail in opposite directions.** `[ $foo = bar ]` word-splits its operands, so an empty `$foo` leaves `[ = bar ]` and errors `unary operator expected`; `[[ $x == $y ]]` never errors but silently pattern-matches, because an unquoted right-hand side of `==`/`!=` is a glob (`x='abc'` against `y='a*'` matches). Write `[ "$foo" = "bar" ]` with both operands quoted and `[[ $x == "$y" ]]` whenever equality is meant, and invert the rule for `=~` — hold the regex in a variable and expand it unquoted, `re='^[0-9]+$'; [[ $str =~ $re ]]`, because quoting any part of the pattern forces those characters to match literally.
- **`printf "$var"` is a format-string injection.** Any `%` in the data is read as a conversion and consumes a nonexistent argument slot, so `payload='100%s'; printf "$payload\n"` prints `100` with no error, corrupting a structured stream whenever the value came from a tool or a user. Always `printf '%s\n' "$var"` — literal format, data in an argument position — and prefer it to `echo` everywhere, since `echo`'s handling of `-n`, `-e`, and backslashes differs across bash's builtin, `dash`, and platform binaries, and it honors no `--` terminator.
- **Declaring and assigning a command's output in one statement masks its exit status.** `local x=$(cmd)` — and `declare`, `export`, `readonly` identically, at top level as much as inside a function — reports the declaration builtin's own status, essentially always 0, so a failing `cmd` reads as success to both `$?` and `set -e` (SC2155). Split the statements: `local foo; foo=$(mycmd)`.
- **`set -e` is off inside a function called from a conditional.** Testing a function in `if`/`while`/`until`, as a non-final command of an `&&`/`||` list, or under `!` disables errexit for that function's entire body and everything it calls, and the ERR trap does not fire there either (SC2310, an optional check that is silent by default). Never call an abort-on-error function from a conditional position. A function whose status a caller captures cannot rely on errexit at all: propagate inside it (`cmd || return`) and read it at the call site with `rc=0; validate_input || rc=$?`, since `validate_input; rc=$?` is dead code — errexit aborts at the failing call before `rc=$?` ever runs.
- **`set -e` does not reach inside a command substitution.** The `$( … )` subshell runs with errexit disabled, so commands after a failing one still run and their output still lands in the result, and only the substitution's last status is visible outside — `x=$(false)` aborts, `x=$(false; printf 'ran\n')` does not. Guard at the call site: `x=$(cmd) || { printf 'cmd failed\n' >&2; exit 1; }`. `shopt -s inherit_errexit` propagates errexit into the subshell and closes the hole, but it is bash 4.4+ and absent on macOS `/bin/bash`, so write the call-site guard as well and never in its place.
- **`(( i++ ))` and `let i++` return non-zero when the pre-increment value is 0.** An arithmetic command's status is 1 when the expression evaluates to 0 (and also on an evaluation error such as division by zero), and post-increment evaluates to the old value, so a counter starting at zero reports failure on its first pass — `let i++` aborts an errexit script on bash 3.2 and on bash 5, while `(( i++ ))` aborts on bash 5 and not on 3.2, which splits this trap across `/bin/bash` and `bash` on the same macOS machine. Write `i=$(( i + 1 ))`, an assignment and therefore always status 0.
- **A legitimately non-zero status still aborts under `set -e`.** `grep -q` returning 1 for no match is the classic case, and `set -o pipefail` extends the hazard to every stage, so `false | true` aborts on the `false` even though the last stage succeeded. Write `… || true` where non-zero is an expected answer; for a pipeline whose per-stage failure must be read, copy the array in the same statement and read the failing stage out of the copy — `cmd1 | cmd2 || stages=("${PIPESTATUS[@]}")` — because every following simple command overwrites `PIPESTATUS`, `rc=$?` included, and under `pipefail` the errexit abort fires before a separate statement runs at all.
- **`cmd | while read …` runs the loop body in a subshell.** Every variable, counter, and array built inside is discarded when the loop ends, with no error at all, surfacing later as "the counter is always 0". Read from a process substitution instead — `while IFS= read -r line; do …; done < <(cmd)` — and give the producer its own status check, because that form leaves a failing producer invisible to both `$?` and `PIPESTATUS`.
- **A foreground child inherits the parent's stdin and can drain it.** A helper invoked from a loop that is itself reading a request stream consumes bytes the parent still needed, or blocks waiting on input nobody meant to give it, silently on both sides. Redirect every foreground child that has no business reading stdin: `some_command < /dev/null` — never `0<&-`, since closing descriptor 0 makes the child's next `open()` land on it.
- **Everything a script emits that is not its payload belongs on stderr.** A diagnostic written without `>&2` lands in the data stream, `cd` prints the resolved directory to stdout whenever it reaches a relative target through a `CDPATH` entry, and `cmd 2>&1 > file` sends stderr to the *original* stdout rather than to the file, because redirections are applied left to right. Write `printf '…\n' >&2` for diagnostics, `cd "$dir" > /dev/null` inside any capture, and `cmd > file 2>&1` in that order.
- **`read` without `-r` and without a leading `IFS=`.** Without `-r`, backslash is an escape character, so `\n`, `\t`, and `\\` in a JSON-escaped string or a Windows path are consumed or transformed; without `IFS=`, even a single-variable read strips leading and trailing whitespace and silently reformats indented input (SC2162). Write `IFS= read -r line` unless backslash line-continuation is genuinely wanted.
- **Bash-4 constructs fail two different ways on a bash 3.2 target.** `shopt -s inherit_errexit`, `globstar`, and `lastpipe` are rejected as invalid option names — which aborts the script when errexit is already on, and leaves `**` matching a single directory level instead of recursing — while `mapfile`, `declare -A`, and `${var^^}` are absent outright, and `"${arr[@]}"` on a declared-but-empty array under `set -u` is an `unbound variable` abort on every bash before 4.4. Gate each behind the minor it actually needs rather than a blanket major — `globstar` and `mapfile` are 4.0, `lastpipe` is 4.2, `inherit_errexit` is 4.4 — and write the gate as `if (( BASH_VERSINFO[0] > 4 || (BASH_VERSINFO[0] == 4 && BASH_VERSINFO[1] >= 2) )); then …` inside a conditional rather than as a bare `(( … ))` statement. Write `"${arr[@]+"${arr[@]}"}"` wherever stock macOS `/bin/bash`, still 3.2.57, has to run.
- **BSD/macOS and GNU tools diverge flag by flag.** `sed -i` requires a backup-extension argument on BSD and takes an optional one on GNU, so bare `sed -i` fails on BSD and `sed -i ''` makes GNU read `''` as the script — the glued `-i.bak` is the only form both accept; `stat -c %Y` is `stat -f %m`; BSD `date` has no `-d`; `grep -P`, `find -printf`, and `mktemp --suffix` are GNU-only, while `find -maxdepth` is an extension both GNU and current BSD accept. Prefer a portable formulation — temp file plus `mv` over `sed -i`, `grep -E '[0-9]+'` over `grep -P '\d+'`, `find … -exec … +` over `-printf` — branch on the platform only where none exists, and do not assume a tool's other flags diverge because one does: check `readlink -f` and `sort -V` against your minimum supported macOS rather than avoiding them on reputation.

## Doc-comment convention: Google Shell Style Guide function header

Every function that is not *both* obvious and short carries a header comment, and every function in a sourced library carries one regardless of length or complexity. Use the five fields — Description, `Globals:`, `Arguments:`, `Outputs:`, `Returns:` — and write only the applicable subset; the style guide's own examples drop the fields they do not need rather than writing them empty. Minimal-correct example:

```bash
#######################################
# Delete a file in a sophisticated manner.
# Arguments:
#   File to delete, a path.
# Returns:
#   0 if thing was deleted, non-zero on error.
#######################################
del_thing() {
  rm -- "$1"
}
```

`Globals:` lists the shell state the function reads or mutates outside its own locals. `Returns:` documents a status other than the default exit status of the last command run; `Outputs:` documents what lands on stdout versus stderr, which is load-bearing for any function whose stdout a caller captures. An underscore prefix for private helpers is a project-level convention with no basis in the style guide — adopt it if the tree already does, but do not attribute it to Google. A generator's tag vocabulary (`@description`, `@arg`, `@exitcode`, `@internal`) may be layered on top of this header when a project has chosen one; it is never the standard on its own.
